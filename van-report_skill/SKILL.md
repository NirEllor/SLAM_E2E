# /van-report — University Report Generator for Stereo Visual-SLAM Projects

Arguments passed: `$ARGUMENTS`

Parse `$ARGUMENTS`. The expected form is `<repo-path>` (absolute path to the target repository).

## Dispatch

### `<repo-path>` — Generate full verified academic report

Generate a ≤20-page formal university report (`report.docx`, `report.pdf`) plus a `problem.pdf` itemizing any unverifiable/missing content. The skill analyzes the repository at the given path directly, never uploads it, may execute the project's own code to reproduce outputs, and produces three deliverables in the target repo root.

**CRITICAL RULE: Anti-Fabrication Spine**

> No sentence containing a number, statistic, function name, file path, line number, or figure reference may be typed into any report file directly. Every such claim must first exist as an entry in the Evidence Ledger (`.van_report_work/evidence_ledger.json`) with status `VERIFIED`. Anything unverifiable goes to `problem.pdf` instead, never silently omitted or guessed.

## Required Report Structure (Content Contract)

Every report generated by this skill must follow this exact structure. Each section has mandatory components and required narrative content. All numeric claims, function names, file paths, and figure references must be verified against the Evidence Ledger before inclusion.

### Section 1 — Introduction and Overview

**Mandatory subsections:**

1. **Background**: Brief explanation of the system (trajectory estimation from stereo camera video), what a visual navigation system does, and why this particular architecture was chosen.

2. **Significance**: Explain the importance of the problem domain (vision-based navigation, SLAM) and its real-world applications in robotics/autonomous systems.

### Section 2 — Code Organization

Present the code structure and implementation locations for all 9 pipeline stages (see Phase 1 for the exact list). Each stage must include:
- **Stage name and brief description** of what it does
- **Function name(s)** implementing the stage
- **File path and line number(s)** (exact locations verified via grep/read)
- **Role in the pipeline** (how it contributes to the overall system)

The code must be readable and well-documented (verify this via code inspection, flag undocumented sections in `problem.pdf`).

### Section 3 — Performance Analysis

A detailed quantitative and qualitative analysis of system performance. The section opens with experiments demonstrating improvements, then presents mandatory statistics, then detailed performance graphs.

**3a. Experiments & Improvements** (FIRST — must all be present if experiments exist):
- Five comparison/ablation studies documenting what was tested, why, and measured impact:
  1. Loop-closure gating — strictness threshold variants
  2. Keyframe density — dense/baseline/sparse distance thresholds
  3. Bundle noise model — prior/stereo sigma sensitivity
  4. PnP-RANSAC parameters — threshold/iteration sensitivity
  5. Feature detectors — AKAZE vs ORB vs SIFT comparison
- Each topic accompanied by 3 figures: trajectory overlay, absolute error, and scalar metrics comparison
- Narrative must state: "We tested X because [motivation], and found that [improvement/trade-off]"
- Addresses PDF requirement: "Where relevant, describe what you did to improve weak points, what the change you implemented was and what impact it had"

**3b. Mandatory Tracking Statistics** (SECOND — must all be present):
- Total number of tracks
- Number of frames
- Mean track length
- Mean number of frame links (connectivity)
- A graph: number of matches per frame
- A graph: percentage of inliers per frame

**3c. Key Performance Graphs** (THIRD — must include all 16, with exact requirements per graph):

1. **Connectivity Graph**: For each frame, the number of tracks linking to the next frame. Axis units: frame ID (x), track count (y).

2. **Track Length Histogram**: Distribution of feature track lifespans. Must use log scale for histogram bins if track lengths span multiple orders of magnitude. Axis units: track length (frames), count.

3. **Trajectory Comparison (Bird's Eye)**: Overlay all four trajectory estimates + ground truth: PnP estimation (blue), Bundle adjustment (orange), Pose Graph without loop closure (red), Pose Graph with loop closure (purple), Ground Truth (green). Axis units: X/Z camera coordinates (meters).

4. **Bundle Optimization Error**: Mean factor-graph error before and after optimization for each bundle window, plotted by the window's starting keyframe. Show both mean and (if available) median. Axis units: keyframe index (x), error magnitude (y, pixels or reprojection error in appropriate units).

5. **Bundle Projection Error**: Median projection error of landmarks in each bundle window, before and after optimization. Axis units: keyframe index (x), median error (y, pixels).

6a. **Track Link Error vs. Distance (PnP)**: Median projection error as a function of distance from the reference frame, for PnP method. If a representative subset of tracks was used (e.g., sampled randomly), state the sampling method and sample size. Axis units: distance (meters, x), error (pixels, y).

6b. **Track Link Error vs. Distance (Bundle)**: Same as #6a but for Bundle adjustment method.

7. **Absolute PnP Estimation Error**: Four subplots or panels showing X-axis error, Y-axis error, Z-axis error (all in meters), and total location error norm (meters) compared to ground truth. Include angle error in degrees as a fifth subplot. Axis units: frame index or keyframe index (x), error in meters/degrees (y).

8. **Absolute Pose Graph Error (No Loop Closure)**: Same as #7 but for the pose graph **before** adding loop closures. Axis units: frame/keyframe index (x), error in meters/degrees (y).

9. **Absolute Pose Graph Error (With Loop Closure)**: Same format as #8 but **after** adding loop closures. Show the improvement from #8 → #9.

10. **Relative Error Between Consecutive Keyframes**: Show relative pose estimation error (location and angle) between every two consecutive keyframes, comparing Bundle and PnP estimates to ground truth. **Required prose**: explicitly state whether the data suggests any doubt about the accuracy of the ground-truth poses themselves (e.g., if errors are systematically biased or inconsistent).

11. **Relative PnP Error over KITTI Sub-segments**: Relative pose error (PnP) evaluated on fixed-length sequence windows (100, 400, 800 frames). Plot both location error (%) and angle error (deg/m). **Required prose**: for each segment length (100, 400, 800 frames), state the **single averaged number** (mean or median) for location error across all segments of that length, and the corresponding angle error for PnP.

12. **Relative Bundle Error over KITTI Sub-segments**: Same as #11 but for Bundle adjustment method; state averaged location and angle error for each segment length.

13. **Loop Closure Match Statistics**: For each successfully verified loop closure, show the number of matches found and the inlier percentage after RANSAC consensus filtering. Axis units: loop closure index (x), count/percentage (y).

14. **Uncertainty Size vs. Keyframe (Location, No Loop Closure)**: Time series of location uncertainty (e.g., sqrt(det(Sigma_xy)) if measuring 2D uncertainty ellipse area) across keyframes **before** adding loop closures.

15. **Uncertainty Size vs. Keyframe (Location, With Loop Closure)**: Same as #14 but **after** adding loop closures, showing uncertainty reduction.

16. **Uncertainty Size vs. Keyframe (Angle)**: Overlay two time series of angle uncertainty across keyframes: one before loop closure, one after. **Required prose**: state exactly how uncertainty size was measured (e.g., "sqrt(det(covariance submatrix))") and how different components were isolated if applicable (e.g., "we extracted the XZ submatrix of the full 6×6 pose covariance"). This must be grounded in the actual code/formula found, never assumed or invented.

**Per-Figure Requirements** (applies to all 16 graphs):
- Every axis must have labeled units
- Figures must be cropped or zoomed to show the relevant data range (drop irrelevant dead zones)
- Comparable graphs (e.g., error plots for PnP vs. Bundle vs. Pose Graph) must use identical scales to enable visual comparison
- Log scale should be used where appropriate (explicitly recommended for Track Length Histogram, Connectivity if ranges are large, and Covariance/Uncertainty-Size graphs)
- Every figure's caption must include the exact code location (file name and line number) that generated it
- Every figure must be immediately followed by a **Graph Analysis** paragraph (ledger-backed) explaining: (a) what the graph shows, (b) whether each trend is positive or negative, (c) what aspect of system performance it demonstrates

**Weakness Mitigation** (optional, only if discoverable evidence exists):
- If any weakness or limitation was identified in an early iteration and a specific change was made to address it, describe: (a) what the weakness was, (b) the exact change implemented, (c) the measured impact on this graph or related metrics
- Only include if evidence exists (git log, code comments, before/after artifacts); never fabricate a mitigation narrative
- Mark any mitigation text as "Implemented fix" or similar to distinguish it from base functionality

### Section 4 — Discussion and Conclusions

**Mandatory subsections:**

1. **Summary and Critique** (Self-critical analysis):
   - Summarize the overall approach and key findings
   - Identify weak points, unrealistic assumptions, or aspects that could be improved
   - Be honest about limitations and potential failure modes

2. **Future Work** (with Real Evidence if `improvements/` folder exists):
   - If `code/project/improvements/` folder exists with results from robust pose-graph techniques:
     * **Switchable Constraints** (Sünderhauf & Protzel, IROS 2012) — cite exact function names/file paths, cite baseline vs. switchable-constraints metrics from `improvements/results/*.pkl`
     * **Dynamic Covariance Scaling** (Agarwal et al., ICRA 2013) — cite exact function names/file paths, cite baseline vs. DCS metrics from `improvements/results/*.pkl`
     * **Stress Test Results** — cite findings from loosened-gate injection tests showing robustness comparison
   - Otherwise: propose concrete directions for system improvement, suggest research directions or algorithmic enhancements, discuss scalability or robustness challenges

3. **Extra Features** (if applicable):
   - If additional experiments, ablations, or features exist beyond the minimum assignment, describe what was researched/implemented, why, and what results were achieved
   - Check for an `experiments/` or `ablations/` sibling directory with matching output artifacts (`experiment_results/`, `outputs/`) as evidence
   - Describe findings in the same ledger-backed style: cite exact functions and output files, never invent results

## Phase 0 — Setup & Environment Resolution

**Step 1: Locate target repo and verify it's a VSLAM-like pipeline.**

Confirm the passed `<repo-path>` exists and contains recognizable pipeline structure:
- Look for `main.py` or similar driver (typical entry point).
- Look for a directory with modules like `tracking.py`, `geometry.py`, `bundle_adjustment.py`, `pose_graph.py` (utilities).
- Look for assignment specs: search for `reports/` dir and try `pdftotext reports/Project\ Submission.pdf` (or similar) to extract the authoritative rubric. If no PDF found, note this as a `NOTED-DISCREPANCY` in the Ledger.

If any of these fail, stop and report that the repo structure is unrecognizable, and exit with a non-zero code.

**Step 2: Locate and validate the canonical implementation tree.**

If the repo contains multiple candidate entry points (e.g. `code/project/main.py` and `code/homework/ex1.py`), run the canonicality-scoring procedure from `scripts/canon_decision.py`:
- Score each candidate on: completeness (implements all required pipeline stages?), recency (git log), executability (does it import cleanly?), output correspondence (does an outputs/ dir exist?), match against the assignment spec structure.
- Pick the highest-scoring tree as canonical.
- Record this decision as an auditable Ledger entry (`CANON-DECISION`) with the scores and reasoning.

**Step 3: Locate the project's own Python venv.**

The skill must run code inside the project's existing venv (which has the project's dependencies: numpy, opencv, gtsam, etc.), not in a fresh separate venv.

```bash
find <canonical_tree_root> -name "pyvenv.cfg" | head -5
```

For each result, validate that `bin/python` (or `bin/python3`) can import the project's core deps:
```bash
<venv>/bin/python -c "import numpy, cv2, gtsam; print('OK')" 2>&1
```

Pick the first one that succeeds. If none succeeds, stop — cannot reproduce code outputs without the project's environment.

**Step 4: Install report-rendering tooling.**

Into the project's venv, pip install (idempotent):
```bash
<venv>/bin/python -m pip install --quiet python-docx reportlab pypdf 2>&1 | tail -3
```

If any package fails to install (e.g. PyPI unreachable, network error), record this as a tooling-degradation entry in the Ledger and note that the skill will attempt a Windows-native fallback (Word COM) or stop with a clear error in `problem.pdf`.

**Step 5: Create scratch directories.**

```
<repo-path>/.van_report_work/
  evidence_ledger.json           # append-only, per-run Ledger
  gap_fixes.log                  # logged self-fixes (if any)
  content_model.json             # assembled report content (structured, no prose)
  <intermediate files>           # search results, classification tables, etc.
```

## Phase 2 — Required-Graph/Stat Inventory & Classification (Performance Analysis — Section 3)

Enumerate all required statistics and graphs from the content contract (6 mandatory tracking statistics + 16 key performance graphs). For each:

1. **Check for existing artifacts**: does a PNG/image file or cached table matching this requirement already exist in an `outputs/` directory or similar under the canonical tree? If yes, classify as `EXISTS-ON-DISK`, record the file path, and measure freshness (does the file's mtime suggest it was generated recently relative to the code?).

2. **Check for plotting/stats code**: does the source tree contain a function that generates this stat/graph? Invoke `scripts/gap_classifier.py <repo-path> <canonical_tree_root> "<stat/graph_name>"` to search for it.

3. **Classify the result**:
   - `EXISTS-ON-DISK`: PNG exists, freshness OK → mark `VERIFIED`, cite the file.
   - `REPRODUCIBLE-BY-RERUN`: code exists and calls `savefig` / writes output, but no artifact on disk (or artifact is stale) → mark `PENDING`, record the function name and invocation command.
   - `FIXABLE-GAP-ADD-SAVEFIG`: code exists and is correct, but never persists an artifact (builds matplotlib figure in memory with no `savefig` call in function or caller) → mark `PENDING-FIXABLE`, record the function name and line where `savefig` should be added (only if self-fix is authorized).
   - `TRUE_GAP`: no implementation found after exhaustive search, or code is fundamentally unrunnable → mark `TRUE_GAP`, record all search commands run.

4. **Per-Graph Narrative Verification** (for graphs #10, #11/12, #14/15/16 from the content contract — Relative Error Between Keyframes, KITTI Sub-segments, Uncertainty Size):
   - Graph #10 (Relative Error Between Keyframes): verify that code or data exists to answer "does the data suggest doubt about ground-truth accuracy?" — search for git commits mentioning ground truth, code comments flagging outliers/anomalies, or alternative-GT comparisons. If no such evidence exists, create a `NARRATIVE-GAP` ledger entry noting that the question cannot be answered from available data.
   - Graphs #11/12 (KITTI Sub-segments for PnP and Bundle): verify that numeric summaries (averaged location error and angle error per segment length 100/400/800) are extractable from the underlying computation (grep for `compute_kitti_sequence_errors` or similar, check if it returns per-segment data). If the function only returns a single global number, mark `NARRATIVE-GAP` — the graph exists but required sub-numbers are missing.
   - Graphs #14/15/16 (Uncertainty Size — Location without LC, Location with LC, Angle): verify that code docstrings, comments, or function signatures reveal exactly how uncertainty is computed (e.g., "sqrt(det(Sigma_xy))"). Search for `uncertainty`, `covariance`, `sqrt`, `det`, or similar keywords in the relevant function. If the formula is undocumented, create a `NARRATIVE-GAP` entry and flag this in the report prose as "measurement method not documented in source code."

Append each to the Ledger under `id: GRAPH-<name>`, `STAT-<name>`, or `NARRATIVE-GAP-<name>`.

## Error Handling & Fallbacks

**If python-docx/reportlab installation fails:**

- Record the failure as a tooling-degradation entry in the Ledger.
- Check if native Windows Word COM is available (Windows only): attempt to drive `Word.Application` to create a docx from a templated RTF or HTML, then use Word's `ExportAsFixedFormat` to generate a PDF.
- If Word COM also fails or is unavailable, record both failures in `problem.pdf` and stop with exit code 1 — never fabricate placeholder deliverables.

**If repo structure is unrecognizable (Phase 0):**

- Exit with a clear error message: "Repo at <path> does not appear to be a stereo visual-SLAM project (missing expected entry point or module structure)."
- Return exit code 1.

**If assignment spec PDF is not found:**

- Note this as a `NOTED-DISCREPANCY` in the Ledger: "Assignment rubric PDF not found; using hardcoded requirement checklist."
- Proceed with the hardcoded checklist but flag this in `problem.pdf` as a caveat (the report's claims are checked against a generic checklist, not the actual rubric).
